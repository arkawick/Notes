## 2. Purpose / Job Description

**What does this job actually do?**
⚙️
```bash
for url in `cat JOB_LIST` ; do
  curl -f -X POST -u "admin:$JENKINS_TOKEN" "$url"enable
done
```
It reads the uploaded file `JOB_LIST` (one job URL per line, ending in `/`) and POSTs `<url>enable` for each one.

**Why is this job required?**
It restores **exactly** the jobs that were enabled before maintenance. Jobs that were disabled on purpose stay disabled.

## 5. Expected Output

- Every job in `JOB_LIST` is enabled again
- Jobs that were disabled before maintenance (not in the list) are still disabled
- Scheduled jobs start running again at their next timer

## 6. Output Validation / Success Criteria (Mandatory)

### Level 1: Jenkins
- **SUCCESS**. With `curl -f` and `bash -e`, any failed POST fails the build, so green means **every** listed job was enabled.
- On failure, the console shows which URL failed. Every job **after** it in the list is still disabled.

### Level 2: Git / Mirror
N/A. Verify through the API:
```bash
curl -s -u admin:<token> https://codesync.ptc-stage.sony.co.jp/api/json \
  | jq -r '.jobs[] | select(.color != "disabled") | .url' | sort > now.txt
sort jobs.txt | diff - now.txt          # expect no differences
```

### Level 3: Manifest
N/A. Spot-check that jobs disabled on purpose are still grey.

### Level 4: Sync validation
Over the next schedule cycle, the mirror jobs (01) and `monitor_refs_*` (15) run and succeed on their own. This confirms the node and credentials survived the maintenance.

**Known risks** (🧭 from reading the config):

| Risk | Detail | Mitigation |
|---|---|---|
| Stops at the first failure | `-f` + `bash -e`: one deleted or renamed job in the list (e.g. a job removed by a deploy during maintenance) aborts the rest | Remove that line from the file and rerun. Already-enabled jobs are unaffected. |
| URLs use the old hostname | The URLs come from `maintenance_store_jobs`, which queries `stage-codesync.ajdc.sony.co.jp` | ❓ Confirm that host still reaches this Jenkins. Otherwise `sed` the URLs to `codesync.ptc-stage.sony.co.jp` before uploading. |
| CSRF crumb | A POST with a password (not an API token) may need a crumb | ❓ Test on stage |

## 8. Recovery / Rerun Procedure

**Is rerun safe?** **Yes.** Enabling an already enabled job is a no-op. Rerun with the same file after fixing a failed line.

**Before rerun check:**

| Check | How |
|---|---|
| Is `maintenance_enable_jobs` itself enabled? | Its page must not say *"This project is currently disabled"* |
| Is it the right list? | The `jobs.txt` from the store run **before** the disable. Line count is plausible. The host matches this instance. |
| Did the previous build partially enable jobs? | Yes, up to the failed URL. Harmless. Rerun the whole list. |
| Does any listed job no longer exist? | Remove it from the file (that is what causes `curl: (22) … 404`) |
| Is Jenkins healthy? | Nodes online, credentials present, plugins loaded, *before* re-enabling scheduled work |
| Does anything need rollback? | A wrong list re-enabled too much → disable the extra jobs by hand, or rerun 17 and then this job with the correct file |

**Rerun steps:** *Build with Parameters* → upload `jobs.txt` → Level 2 diff is empty.
