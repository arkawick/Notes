  What the job does

  index_pp_apps.yaml runs manage.py index_pp_apps --jobs 1 every hour from 08:00
  to 20:00. For each build ("label") in platform/systemmanifest created in the
  last day that hasn't been indexed yet, the command does this
  (product_packages/management/commands/index_pp_apps.py):

  1. Asks C2D for the build's package list, and looks for a tools-imagetools*
     package, which contains the aapt tool.
  2. Finds the platform/vendor/semc/build/composition-config repo in the build,
     clones it at the build's revision, and parses each variant_specs/pp-*.xml
     file.
  3. For every app-* package a PP depends on, downloads the .deb from C2D,
     unpacks the .apk, and runs aapt dump badging to read the app's display
     name.
  4. Saves the results to the LabelProductPackages and ProductPackageApp tables.

  What its "output" is

  The console output is only logging. The useful result is database rows, which
  are shown in two places:
  - The "Apps" tab on a build page, /builds/<manifest>/<label>/+apps. The tab
    comes from explorer/templates/explorer/label_tabs.html:73 and is filled by
    label_apps_list in explorerutils.py:273. It shows a table of apps against
    PPs.
  - /product_packages/<label>/, which shows the same table.

  Why it would now return nothing, without any error

  Every step above needs something from the old build process: C2D package
  metadata, a tools-imagetools package, the composition-config repo in the
  build, and pp-*.xml files. If a build lacks any of them, the command skips it
  with continue. The most likely failure point logs nothing at all: if there's
  no tools-imagetools package, the build is skipped silently. So an Ithaca build
  that lacks these would produce a green Jenkins run with an empty log and no
  new rows. That matches what the reporter describes.

  4. Stores the result in CMWEB's database.

  tab on a build page (/builds/<manifest>/<label>/+apps, also at
