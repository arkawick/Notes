# Development

Everything here runs from the `cmweb-project` checkout (`site/` in a deployed or Jenkins workspace).
The build system is a Makefile and assumes Linux — it shells out to `apt-get`, `lsb_release` and
`somc-virtualenv3`.

## Getting the code

The three repositories must sit in the layout the manifest defines; a plain `git clone` of one of them
is not enough to run anything.

```bash
repo init -u git://review-plus.ptc.sony.co.jp/cmweb-manifest -b cloudj2
repo sync
```

This produces `site/` (= `cmweb-project`) with `site/apps/` (= `cmweb-app`) inside it. Use
`-m release.xml` for the pinned release manifest instead of the default floating one.

> This document supersedes `cmweb-project/README.rst`, whose content has been merged here.

## Environment setup

```bash
cd site
make install                      # apt packages + virtualenv at ../ENV + pip requirements
make install NO_APT_INSTALL=1     # skip sudo apt-get (Jenkins agents pre-install them)
make install VIRTUALENV_DIR=../.virtualenv   # somewhere other than ../ENV
source ../ENV/bin/activate
```

`make install` is a dependency of most other targets, and is stamped with marker files
(`../ENV/.cmweb-pip-freeze.list`, `$VENV_PARENT/.cmweb-apt-get.list`), so repeat runs are cheap.
Requirements are chosen by Ubuntu release: `etc/requirements-20.txt` (Django 4.2) or
`etc/requirements-22.txt` (Django 5.2).

The virtualenv is created *outside* the project directory (`../ENV` by default, i.e. next to `site/`),
which is why every Makefile target invokes `../ENV/bin/python3` rather than assuming an active shell.
Activate it by hand when running `manage.py` directly:

```bash
source ../ENV/bin/activate
```

Two optional system packages, needed only for particular areas of the code:

```bash
sudo apt-get install python-ldap              # the users app's LDAP authentication
sudo apt-get install graphviz libgraphviz-dev # django-fsm state transition diagrams
```

### `cmweb/secure.py` is mandatory

`settings.py` ends with:

```python
try:
    from .secure import *
except Exception as e:
    sys.stderr.write("%r.\n" % e)
```

The failure is swallowed, but names that `secure.py` provides are used **unguarded** further down —
`OPENSEARCH_HOST`, `OPENSEARCH_AUTH_USERNAME`, `OPENSEARCH_AUTH_PASSWORD` — so without the file Django
dies with a bare `NameError` on `OPENSEARCH_HOST` rather than anything that explains itself. A minimal
local file:

```python
OPENSEARCH_HOST = 'localhost'
OPENSEARCH_AUTH_USERNAME = ''
OPENSEARCH_AUTH_PASSWORD = ''
```

Deployed environments additionally need `DATABASES__DEFAULT__{HOST,PORT,NAME,PASSWORD}`,
`CACHES__DEFAULT__{HOST,PORT}` and `AUTH_DEFAULT_SERVICE_{USERNAME,PASSWORD}` — see
`cmweb-scripts/ansible/roles/cmweb-node/templates/django/secure.py.j2`. `secure.py` is gitignored and
must never be committed.

### Settings modules

| Module | Use |
| --- | --- |
| `cmweb.settings` | Default for `manage.py`. SQLite, `DEBUG = True`, local-memory cache, eager Celery |
| `cmweb.dev_template` | Template to copy for a personal dev settings module (Postgres + memcached) |
| `cmweb.settings_test` / `_stage` / `_prod` | Deployed environments |
| `cmweb.settings_deployed` | Symlink to one of the above, created by Ansible. What Celery expects |
| `cmweb.settings_management` | Generated by Jenkins for backend jobs; adds an `[Env][Backend]` mail prefix |

Environment-specific configuration belongs in its own settings module, not in edits to `settings.py`;
`cmweb/dev_template.py` is the worked example to copy.

### The LDAP service account

Single sign-on through Kerberos and LDAP needs a bind account, which can be supplied two ways:

- `AUTH_DEFAULT_SERVICE_USERNAME` / `AUTH_DEFAULT_SERVICE_PASSWORD` in the settings module (in practice,
  written into `secure.py` at deploy time), or
- the `users-serviceusername` / `users-servicepassword` `Parameter` rows in the admin.

**The `Parameter` values win** — `users/auth.py` reads
`Parameter.get(SERVICE_USERNAME_KEY, settings.AUTH_DEFAULT_SERVICE_USERNAME)`, so the settings value is
only the fallback. Rotating the account in the admin therefore takes effect without a redeploy, and a
stale `Parameter` row silently overrides a correct `secure.py`. The same pattern covers the Gerrit,
JIRA, Jenkins and M+ service accounts (`gerrit-serviceusername`, `jira-serviceusername`, …).

## First run

```bash
make db                     # manage.py migrate --noinput
./manage.py createsuperuser
./manage.py runserver 0:8000
```

Browse to `http://localhost:8000/admin/` and log in as the superuser. Two pieces of setup are needed
before the site is usable, because both are data rather than code:

1. **Create the home page.** `/` is served by the `generic_pages` app, which is included *last* in the
   root URLconf as the catch-all. With no page in the database the root URL 404s. In the admin, under
   **Base → Generic pages**, add a generic page titled `Home` with any body text, then check that
   `http://localhost:8000/` renders it.
2. **Fix the site domain.** Under **Sites → Sites**, change the default `example.com` entry to the
   domain you are serving from. Feeds and absolute URLs in outgoing mail are built from it; deployed
   environments pin a specific row through `FEED_SITE_ID` (17 in production, 20 in test).

## Getting data into the database

A migrated database is empty, and most of CMWEB is a view onto indexed data. Two ways to fill it:

**Load the test fixture** — fastest, and what the tests use:

```bash
make install-testdata     # loaddata apps/explorer/fixtures/testdata.json — best on a fresh DB
```

**Index real data** — needs the git mirrors described below, plus two admin entries:

- **Explorer → Included branch rules**: add a rule for `platform/manifest` with a pattern narrow enough
  to stay manageable, e.g. `^n-yoshino`. Without an inclusion rule CMWEB will index *nothing*; with a
  broad one it will try to index every manifest branch that has ever existed.
- **Explorer → Repositories**: add `platform/amssmanifest` so modem builds are picked up alongside the
  platform ones.

Then run the indexing commands (`index_labels`, `index_latest`, `sync_commits`,
`sync_projects_from_gerrit` …). The first run takes a long while.

> The historic instruction was `./manage.py index_all -v1 --days=0.25`. **That command no longer
> exists** — it was split into the per-area commands above. `make index-testdata` is the closest
> equivalent for a development database.

Regenerating the fixture:

```bash
make index-testdata TESTDATA_SYSTEM_BRANCHES=l-mr1-kitakami2 \
                    TESTDATA_AMSS_BRANCHES=kitakami-8994 \
                    TESTDATA_DAYS=3
make testdata            # dumpdata over TESTED_APPS + auth → apps/explorer/fixtures/testdata.json
```

## Git repositories

CMWEB reads **bare** git repositories straight off the filesystem rather than fetching from Gerrit, so
indexing needs a local mirror at `<PATH_ROOT>/repository` (i.e. alongside `site/`, one level above the
Django project). Production uses Gerrit replication; deployed environments mount the shared mirror over
EFS. For development, reproduce it with `repo`'s mirroring support.

`repo` refuses to create a mirror inside an existing repo tree, so the mirror has to live *outside* the
`cmweb-manifest` checkout and be symlinked in:

```bash
# from the root of your CMWEB workspace
ln -s ../repository

cd ..
mkdir repository && cd repository
repo init -u git://review.ptc.sony.co.jp/platform/manifest.git -b n-yoshino --mirror
repo sync -j4
```

Use the same branch you wrote an inclusion rule for. Refresh at any time with another `repo sync`.

The manifest projects themselves are not part of that mirror and must be cloned bare:

```bash
git clone git://review.ptc.sony.co.jp/platform/manifest     platform/manifest.git     --bare
git clone git://review.ptc.sony.co.jp/platform/amssmanifest platform/amssmanifest.git --bare
```

Finally, fetch the review notes. `repo sync` does **not** fetch `refs/notes/review`, and that ref is
where CMWEB reads each commit's approver, verifier and submitter from — without it, commits index with
empty review metadata:

```bash
repo forall -c git fetch origin refs/notes/review:refs/notes/review
```

This fails on some repositories with `fatal: Couldn't find remote ref refs/notes/review`. That is
expected and harmless: external repositories imported from vendors have no review notes.

## Static files

```bash
make static      # collectstatic + django-compressor
```

`COMPRESS_OFFLINE = True`, so compression is not lazy: a template that references a new CSS/JS file
will not render correctly until `make static` has run. Compression uses the bundled YUI compressor
(`bin/yuicompressor-2.4.8.jar`), which needs a JRE — the default `JSMinFilter` cannot handle some of the
vendored JavaScript. The resulting `manifest.json` hash is read back by `settings.py` into
`GLOBALS['STATIC_MD5']` and served in the `X-PJAX-Version` header.

## Tests

```bash
make test                       # full suite, --keepdb, JUnit XML into ../test-results
make test TEST_VERBOSITY=2
```

`make test` covers `TESTED_APPS`: `base blog explorer users aod cmjenkins dashboards gerritproxy
harvest historian issues packages rebase request vendorsync`. It depends on `static`, so a test run
also compresses assets.

Narrower runs go straight through `manage.py`:

```bash
../ENV/bin/python3 manage.py test explorer --keepdb -v2
../ENV/bin/python3 manage.py test explorer.tests.test_label --keepdb
../ENV/bin/python3 manage.py test explorer.tests.test_label.LabelTestCase --keepdb
../ENV/bin/python3 manage.py test explorer.tests.test_label.LabelTestCase.test_label_detail --keepdb
```

`--keepdb` matters: building the test database and loading the fixture is slow. Drop it when a
migration changed the schema.

Test conventions in this codebase: `LiveServerTestCase` with
`fixtures = ['explorer/fixtures/testdata.json']`, models fetched via `apps.get_model()`, and assertions
made against rendered views through `reverse()` rather than against model internals. The runner is
`xmlrunner.extra.djangotestrunner.XMLTestRunner` so Jenkins can publish results.

## Lint

```bash
make kwalitee
```

Three tools, all of which must pass before review:

| Tool | Configuration |
| --- | --- |
| `pyflakes` | Everything except migrations, `secure.py`, `settings*.py`, `dev_template.py`, `celery.py`, `cmweb/__init__.py` |
| `pycodestyle` | `.pycodestylerc` — 80 columns; excludes `static`, `migrations`, `secure.py`, `settings_management.py` |
| `pydocstyle` | Everything except migrations and `secure.py` |

**pydocstyle over the whole tree is the convention that shapes the code most.** Every module, class and
method needs a docstring, which is why one-line accessors throughout carry `"""Return ..."""`. New code
that omits them fails the gate.

Other house style, visible throughout and worth matching:

- `from builtins import object, str, range` and `from __future__ import absolute_import` at the top of
  most modules — Python 2 compatibility residue; harmless, and consistent.
- `apps.get_model('explorer', 'label')` instead of importing models, in indexing code and anywhere a
  cycle is likely.
- Writes in management commands and tasks go through `using=settings.DATABASE_ALIAS_FOR_WRITE`.
- Nested `class Meta(object):` with its own docstring.

## Review flow

All three repositories are reviewed on Gerrit at `review-plus.ptc.sony.co.jp`; the active branch is
`cloudj2`.

```bash
repo start <topic> .
# edit, commit
repo upload .
```

Pushing a patchset to `cmweb-app` or `cmweb-project` triggers the **`verify_cmweb_changes`** Jenkins
job, which syncs the manifest, applies your patch with `repo download`, generates a settings module,
and runs `make install NO_APT_INSTALL=1` followed by the full `make` (i.e. `clean kwalitee test`). It
votes Verified +1/-1 on the change. Patches to `cmweb-scripts` are verified by
`verify_ansible_playbook` and `verify_jenkins_jobs` instead.

To test a not-yet-merged change inside another Jenkins job, most job templates take a
`GERRIT_DOWNLOAD_LIST` parameter, e.g. `cmweb-project 233738/5, cmweb-app 243932/5`.
