## 2. Purpose / Job Description

**What does this job actually do?**

[Live]

```bash
for url in `cat JOB_LIST` ; do
  curl -f -X POST -u "admin:$JENKINS_TOKEN" "$url"enable
done
```

It reads the uploaded file `JOB_LIST` (one job URL per line, ending in `/`) and POSTs `<url>enable` for each one.

**Why is this job required?**

It restores exactly the jobs that were enabled before maintenance. Jobs that were disabled on purpose stay disabled.

## 5. Expected Output

- Every job in `JOB_LIST` is enabled again
- Jobs that were disabled before maintenance (not in the list) are still disabled
- Scheduled jobs start running again at their next timer

## 6. Output Validation / Success Criteria (Mandatory)

### Level 1: Jenkins
- **Job status:** SUCCESS. With `curl -f` and `bash -e`, any failed POST fails the build, so green means every listed job was enabled.
- **Expected final stage:** one `curl -f -X POST ...enable` per line of `JOB_LIST`
- **No unexpected errors in console log:** on failure, the console shows which URL failed. Every job after it in the list is still disabled.

### Level 2: Git / Mirror
N/A. Verify through the API:

```bash
curl -s -u admin:<token> https://codesync.ptc-stage.sony.co.jp/api/json \
  | jq -r '.jobs[] | select(.color != "disabled") | .url' | sort > now.txt
sort jobs.txt | diff - now.txt          # expect no differences
```

### Level 3: Manifest
N/A. Spot-check that jobs disabled on purpose are still grey.

### Level 4: Sync validation
Over the next schedule cycle, the mirror jobs and `monitor_refs_*` run and succeed on their own. This confirms the node and credentials survived the maintenance.

## 8. Recovery / Rerun Procedure

**Is rerun safe?** Yes. Enabling an already enabled job is a no-op. Rerun with the same file after fixing a failed line.

**Before rerun check:**

- [ ] **Was the upstream source available? (`git ls-remote`)** N/A for git. `maintenance_enable_jobs` itself must be enabled (its page must not say *"This project is currently disabled"*), and Jenkins must be healthy: nodes online, credentials present, plugins loaded.
- [ ] **Did the previous build partially push anything?** Yes, it enabled jobs up to the failed URL. Harmless; rerun the whole list.
- [ ] **Is the Jenkins workspace clean?** Not relevant. Is it the right list? The `jobs.txt` from the store run before the disable, with a plausible line count and a host that matches this instance.
- [ ] **Is another CodeSync job running against the same repository?** Instead ask: does any listed job no longer exist? Remove it from the file (that is what causes `curl: (22) ... 404`).
- [ ] **Does anything need rollback or cleanup?** If a wrong list re-enabled too much, disable the extra jobs by hand, or rerun `maintenance_disable_jobs` and then this job with the correct file.
- [ ] **Has the Qualcomm import script changed?** N/A.
- [ ] **Does the script need adapting to support a new branch or tag from the vendor?** N/A.
- [ ] **Should an obsolete branch be moved aside using the service account before rerunning?** N/A.

**Rerun steps:**

1. *Build with Parameters* and upload `jobs.txt`.
2. Confirm the Level 2 diff is empty.

### C. Known risks

[Proposed] From reading the config and the YAML.

| Risk | Detail | Mitigation |
|---|---|---|
| Stops at the first failure | `-f` + `bash -e`: one deleted or renamed job in the list (for example a job removed by a deploy during maintenance) aborts the rest | Remove that line from the file and rerun. Already-enabled jobs are unaffected. |
| URLs use the old hostname | The URLs come from `maintenance_store_jobs`, which queries `stage-codesync.ajdc.sony.co.jp` | [Unconfirmed] Confirm that host still reaches this Jenkins. Otherwise `sed` the URLs to `codesync.ptc-stage.sony.co.jp` before uploading. |
| CSRF crumb | A POST with a password (not an API token) may need a crumb | [Unconfirmed] Test on stage |
| Not managed by JJB | No project YAML uses `template-maintenance.yaml` | Edits to the template change nothing in Jenkins. Back up the live `config.xml` before editing it in the UI. |
| Next deploy overrides the restored state | `code_sync_deploy_jenkins_jobs` runs `make update`, which writes each JJB-managed job's `disabled` flag from the YAML. Once this job re-enables the deploy job, its next run (stage: daily timer or a merge to `stage`; prod: a merge to `master`) sets JJB-managed jobs to their YAML state, whatever `jobs.txt` said. | If a job was disabled by hand before maintenance and must stay off, set `disabled: true` in its YAML as well [Proposed] |
